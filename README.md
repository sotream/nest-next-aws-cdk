# nest-next-aws-cdk

[![CI](https://github.com/sotream/nest-next-aws-cdk/actions/workflows/ci.yml/badge.svg)](https://github.com/sotream/nest-next-aws-cdk/actions/workflows/ci.yml)

AWS CDK (TypeScript) that deploys [nest-next-starter](https://github.com/sotream/nest-next-starter) (a NestJS
API, a Next.js web app, PostgreSQL and Redis) to AWS on ECS Fargate, with an **environment per pull request**.
It is the CDK counterpart of [nest-next-aws-terraform](https://github.com/sotream/nest-next-aws-terraform):
same application, same shape of infrastructure, different tool. The application is deployed unmodified; this
repository is only the infrastructure and the CI/CD around it.

It is a portfolio project that shows how I structure CDK: small single-purpose constructs, one composition
stack, a thin app entry, tests on the synthesised template, cdk-nag as a gate, and a preview flow that
creates, updates and destroys stacks by pull request. **Nothing here has been deployed to an AWS account**;
read [What is verified](#what-is-verified) first.

## What's included

| Area          | Choice                                                                                                |
| ------------- | ----------------------------------------------------------------------------------------------------- |
| Compute       | ECS Fargate: `api` and `web` as separate services behind one ALB, `/api/*` routed to the API          |
| Data          | RDS PostgreSQL (private, encrypted, TLS enforced) and ElastiCache Redis (TLS and AUTH)                |
| Network       | VPC, 2 AZs, public and private subnets, NAT count per profile, flow logs                              |
| Secrets       | Generated by Secrets Manager; URL secrets composed with dynamic references; no value in the template  |
| Edge          | ALB with an optional ACM certificate and Route 53 alias when a domain is set                          |
| Migrations    | One-off ECS task that must exit 0 before the services roll                                            |
| Observability | CloudWatch log groups, KMS-encrypted SNS topic, 11 alarms                                             |
| Previews      | `nest-next-pr-<number>` per pull request, comment with the URL, destroy on close, nightly clean-up    |
| CI/CD         | GitHub Actions with OIDC, no stored keys: `ci`, `deploy`, `preview`, `preview-cleanup`                |
| Guardrails    | cdk-nag AwsSolutions on every synth, template assertions, `cdk diff` and a database-replacement guard |

## Prerequisites

Node 24 and pnpm. For the quality gate nothing else: no AWS account or credentials are needed.

## Quick start

```bash
pnpm install
pnpm run build        # tsc
pnpm run lint         # eslint
pnpm run format:check # prettier
pnpm test             # 80 jest tests, including cdk-nag for every profile
pnpm exec cdk synth -c env=dev --quiet    # also: stage, prod, pr-<number>
```

Deploying is described in the [runbook](docs/runbook.md). It needs an AWS account that you bootstrap yourself;
the agent rules in [CLAUDE.md](CLAUDE.md) forbid `cdk deploy`.

## Configuration

| Input                                                                 | Where                 | Meaning                                             |
| --------------------------------------------------------------------- | --------------------- | --------------------------------------------------- |
| `-c env=<name>`                                                       | CDK context           | One of `dev`, `stage`, `prod`, `pr-<number>`        |
| `-c imageTag=<tag>`, `-c migrateImageTag=<tag>`                       | CDK context           | Image of the services and of the migration task     |
| `DOMAIN_NAME_<ENV>`, `HOSTED_ZONE_ID_<ENV>`, `HOSTED_ZONE_NAME_<ENV>` | environment variables | Public domain, optional                             |
| `ALARM_EMAIL_<ENV>`                                                   | environment variable  | Alarm recipient, optional                           |
| `GITHUB_REPOSITORY`, `GITHUB_OIDC_PROVIDER_ARN`                       | environment variables | Trusted repository; reuse an existing OIDC provider |

Sizes, NAT count, retention, Multi-AZ and removal policy per environment are in [lib/config.ts](lib/config.ts).

## Compared with the Terraform project

| Topic                | nest-next-aws-terraform                              | nest-next-aws-cdk                                                            |
| -------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| Structure            | Modules, one composition module, `envs/<name>` roots | Constructs, one `EnvStack`, profiles as data, thin `bin/app.ts`              |
| Environments         | Three long-lived                                     | Three long-lived plus `pr-<number>` previews                                 |
| State                | S3 bucket with native locking, bootstrapped by hand  | CloudFormation; CDK bootstrap by hand                                        |
| Secrets              | Ephemeral values through write-only attributes       | Generated by Secrets Manager, composed with dynamic references               |
| IAM                  | Written per module                                   | `grant*` and `ecs.Secret` inside a stack; hand-written only for deploy roles |
| Tests                | offline `terraform test`                             | jest assertions on the synthesised template, cdk-nag                         |
| Policy checks        | tflint, checkov                                      | cdk-nag AwsSolutions                                                         |
| Deploy               | `terraform apply` per phase                          | `cdk deploy` per phase, the same migrate-then-roll order                     |
| Review before deploy | `terraform plan` comments on pull requests           | `cdk diff` in the job summary, database-replacement guard                    |

## What is verified

Verified without an AWS account, in CI and locally: `tsc`, eslint, prettier, 80 jest tests on the synthesised
templates (including the secret-read regression test and cdk-nag for every profile), `cdk synth` for every
profile and for the HTTPS variant, gitleaks.

**Not verified, because it needs an account:** an actual `cdk deploy`, that CloudFormation resolves the
dynamic references in the URL secrets, that the migration task and the services start, the deploy, preview and
clean-up workflows and their scripts (they have never run; neither shellcheck nor actionlint was available),
the cost figures, and that alarms reach the SNS topic.

## Known limitations

- Not deployed to any AWS account unless you do it.
- Single region, single account.
- The preview role is **not a sandbox**: CDK deploys through the broad bootstrap execution role, and a pull
  request from this repository can change the workflow and the code. See
  [ADR 0003](docs/adr/0003-preview-lifecycle.md). Give write access only to people you trust.
- Previews have no seeded data and no domain; they run over HTTP and the API runs as `APP_ENV=dev`.
- The smoke test checks only `/api/health/ready` and the sign-in page.
- No ALB access logs and no automatic secret rotation (acknowledged in cdk-nag with reasons).
- Database TLS is `sslmode=no-verify`: encrypted, not authenticated ([ADR 0004](docs/adr/0004-database-tls.md)).
- Stage and prod without a domain synthesise with a warning and run the API as `APP_ENV=dev`.
