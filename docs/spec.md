# nest-next-aws-cdk: technical spec (draft 1)

Status: draft for the owner. The implementing agent reads this file first and works feature by feature (section 9).

## 1. Goal

Deploy [nest-next-starter](https://github.com/sotream/nest-next-starter) (NestJS API, Next.js web app, PostgreSQL, Redis) to AWS with **AWS CDK in TypeScript**, and give every pull request its own **preview environment** that is created on open and destroyed on close.

It is the CDK counterpart of [nest-next-aws-terraform](https://github.com/sotream/nest-next-aws-terraform): same application, same shape of infrastructure, different tool. The portfolio point is to show that the owner can structure CDK code (small constructs, one composition stack, thin app entry, tests, guardrails) and run a per-PR preview flow, not only Terraform.

The application is deployed unmodified. This repository is only the infrastructure and the CI/CD around it.

## 2. Non-goals

- No changes to the application code.
- No multi-account organisation setup, no custom domain requirement (a domain is optional input).
- No Kafka. The starter does not need it for this scope.
- No claim of a production-ready platform. See section 10.

## 3. Principles

1. Constructs are small and single-purpose; one stack composes them; the app entry only reads configuration and instantiates stacks.
2. Least-privilege IAM. Every policy is derived from the resource it protects (`grantRead`, `grantSecretRead` and similar), never a hand-written wildcard. This is a lesson from a real incident where a task role could not read a newly added secret.
3. No secret values in the repository, in the synthesised template or in logs. Passwords are generated by the platform (Secrets Manager) and injected into tasks at start.
4. Preview environments are cheap and disposable: small sizes, one NAT at most, `RemovalPolicy.DESTROY` only for previews, never for `dev` or `prod`.
5. Everything verifiable without an AWS account is verified in CI: unit tests on the synthesised template, `cdk-nag`, lint, format.

## 4. Target architecture

| Area          | Choice                                                                                                   |
| ------------- | -------------------------------------------------------------------------------------------------------- |
| Compute       | ECS Fargate: `api` and `web` as separate services behind one ALB; `/api/*` routed to the API             |
| Data          | RDS PostgreSQL (private subnets, encrypted, backups on non-preview) and ElastiCache Redis (TLS and AUTH) |
| Network       | VPC, 2 AZs, public and private subnets, NAT count configurable (1 for preview)                           |
| Secrets       | Secrets Manager secrets generated by CDK; task execution role reads them at start                        |
| Images        | ECR repositories; images built by CI from a pinned commit of the starter; tags immutable                 |
| Migrations    | One-off ECS task that must exit 0 before services roll                                                   |
| Observability | CloudWatch log groups, SNS topic, alarms for 5xx, CPU, memory, task count, RDS                           |
| Edge          | ALB, optional ACM certificate and Route 53 alias when a domain is configured                             |
| CI/CD         | GitHub Actions with GitHub OIDC to AWS, no stored keys                                                   |

Environments: `dev`, `stage`, `prod` (long-lived stacks) and `pr-<number>` (preview stacks).

## 5. Repository layout

```
bin/app.ts                 app entry: reads config, instantiates stacks
lib/config.ts              typed environment config (sizes, NAT count, retention, domain)
lib/constructs/            network, database, cache, secrets, ecr, service, alarms (one file each)
lib/stacks/                shared-stack (ECR, OIDC role), env-stack (one environment)
test/                      jest tests: fine-grained assertions and snapshot of the template
scripts/                   current-image-tag, smoke test
.github/workflows/         ci, preview, deploy
docs/                      spec, ADRs, runbook, cost estimate
```

## 6. Preview environments

- Trigger: pull request opened or updated against `main`, only from branches of this repository (never from forks).
- Stack name `nest-next-pr-<number>`. Config profile `preview`: 1 NAT, smallest RDS and Redis, 1 task per service, `RemovalPolicy.DESTROY`, log retention 3 days.
- Flow: build and push images for the PR commit, `cdk deploy`, run migration task, smoke-test, post the preview URL as a PR comment (update the same comment on every push).
- Cleanup: on PR close or merge a workflow runs `cdk destroy`. A scheduled nightly job destroys preview stacks whose PR is closed or older than 7 days, as a safety net against orphaned cost.
- Permissions: a separate OIDC role for previews, allowed to act only on resources tagged `env=pr-*`. The role trust policy names the repository and the `pull_request` subject.

## 7. Guardrails

- `cdk-nag` (AwsSolutions pack) runs in tests. Every suppression carries a written reason; no blanket suppressions.
- Tests assert: no `*` in IAM actions except documented cases, RDS and Redis not publicly accessible, encryption at rest on, the execution role can read every secret the task definition references (regression test for the incident above), preview profile uses `DESTROY` and non-preview does not.
- CI checks: `tsc`, eslint, prettier, jest, `cdk synth` for every environment, secret scan.
- Pre-deploy check in the deploy workflow: `cdk diff` is posted to the job summary; a deploy that would replace the database is blocked unless an explicit input allows it.
- ECS deployment circuit breaker with rollback is on.

## 8. Cost and deploy honesty

Nothing is deployed until the owner provides an AWS account and sets the repository variables. The cost estimate in `docs/cost-estimate.md` is calculated from list prices and labelled as an estimate. The README must say which parts were verified (synth, tests, nag) and which were not (an actual deploy), as the Terraform project does.

## 9. Work plan: feature by feature

One GitHub issue per feature, one branch, one small pull request with its own tests, required CI, squash merge. Do not batch features. After each merge, tick it here.

1. Project scaffold: CDK app, TypeScript strict, jest, eslint, prettier, CI workflow `ci` (tsc, lint, test, synth). Config module with the four environment profiles.
2. Network construct and tests.
3. Secrets construct, ECR repositories, tests.
4. Database construct (RDS) and cache construct (Redis), tests.
5. Service construct (Fargate service, task definition, log group, health checks), API and web services, ALB routing, tests including the execution-role secret-read test.
6. Migration one-off task and the deploy workflow (OIDC, build and push images, `cdk diff` summary, smoke test).
7. Alarms and SNS topic.
8. Preview environments: preview workflow, PR comment, cleanup on close, nightly orphan cleanup, preview OIDC role.
9. `cdk-nag` in tests with documented suppressions.
10. Docs: architecture overview, ADRs (why CDK constructs this way, secrets handling, preview lifecycle), runbook, cost estimate, README with a comparison to the Terraform project.

## 10. Known limitations (to keep honest in the README)

- Not applied to any AWS account unless the owner does it.
- Single region, single account assumption.
- Previews share nothing with each other but also get no seeded data.
- The smoke test checks only `/api/health/ready` and the sign-in page.

## 11. Decisions

- D1 (default): TypeScript CDK v2 with `aws-cdk-lib`; no L3 libraries beyond `cdk-nag`.
- D2 (default): GitHub Actions, OIDC, no long-lived AWS keys.
- D3 (default): Node 24, pnpm, same conventions as the starter.
- D4: the repository stays private until the owner decides to publish it.
